# Private Codex runner prototype

This is an isolated per-service-account app-server broker. Source/fixture validation is separate from real provider authentication, paid turns and native resume acceptance. Deployment/resources/credential injection are not authorized by this development checkpoint.

The optional Docker `runner` stage installs ARM64 Codex **0.160.1** with executable SHA256 `fbbaec80443919f86dd63648a0b62759cf6f1d0e09310602fde96885e0bceb3e`. A different artifact fails the build. Experimental protocol fields are version-dependent. The pinned executable's `generate-json-schema --experimental` was checked in Docker without an account/model request; `dynamicTools` needs initialize.experimentalApi and function descriptors need type=function. Upgrading the pin requires fresh schema and integration verification.

Protocol references: [official App Server](https://learn.chatgpt.com/docs/app-server) and [official authentication](https://learn.chatgpt.com/docs/auth). The broker initializes stdio, creates/resumes a thread and reads its persisted turns. Dynamic tool requests return complete JSON results. Original Codex home and broker dispatch reservations survive in `/state`; DB stores owner metadata and a conversation cache, not a separate execution-event database. A failed/interrupted turn is explicit and never automatically replayed.

## Required reviewed inputs

- RUNNER_ACCOUNT_ID: one auth.accounts UUID, matching the API's operator-owned mapping.
- RUNNER_TOKEN_FILE: separate private >=32-char secret for each runner; API mapping points to its private copy. Do not reuse between accounts.
- CODEX_MODEL: an explicitly authorized model; there is no assumed entitlement or selected deployment model.
- CODEX_API_KEY_FILE: optional user-specific, explicitly authorized API key file. It is read only by the adapter, sent through native login and never copied from an agent home or returned in JSON. The current prototype uses ephemeral native credential storage. New personal ChatGPT login integration remains pending the user/PM-selected auth direction; local PM login is never imported.
- RESEARCH_TOOL_CALLBACK_URL: fixed internal API URL, normally `http://api:8080/api/internal/research/tools`; include APP_BASE_PATH when present.
- RUNNER_STATE_DIR: `/state`, one separate retained volume and work/home directory per account.

API CODEX_RUNNERS_FILE is a private JSON mapping `{ACCOUNT_UUID:{"url":"http://dedicated-runner:8080","tokenFile":"/run/secrets/account-runner-token"}}`. It rejects repeated URLs/secrets. Owner ID selects the mapping on the server; browsers cannot choose runner URL/native thread/path. Every runner result must assert that same owner. Native thread IDs are selected from a persistent broker session map, not request paths. API storage-tool tokens bind the owner, platform session, current request, original live login, TTL and current approval/role. Possessing another resource ID or using a different session/turn cannot change this authority.

## Isolation and lifecycle

Each account requires a different container/process, token, state volume and namespace/network policy. A persistent account-id marker rejects other-owner or unbound populated volumes; an exclusive volume lease rejects a second adapter sharing the dispatch ledger. Mount no DB/operator Secret, host/agent home, Docker socket, other-account PVC, kubeconfig or shared workspace. Restrict incoming traffic to the API and outbound internal traffic to its scoped tool callback; deny DB and other runners. Apply read-only root, separate state mount, no capabilities/no-new-privileges, process/memory/CPU limits and provider egress policy. The prototype runs one active turn per runner and returns conflict for additional concurrent dispatches. Its child gets only its own HOME/CODEX_HOME and no inherited API/DB environment. Shell tool is disabled, sandbox is readOnly and unsupported approval/credential-refresh requests fail closed. Broader browsing/model integration requires separate validation; source code does not prove deployment policies.

The API reserves a turn and stores the 202 result atomically before background dispatch. Its retry record does not dispatch again. The runner durably reserves request IDs and fingerprints before native turn start; same request ID with different content conflicts. Original input/key/expectedVersion must survive frontend reconnect, even after polling changes the session revision. Runner restart retains original records, marks ambiguous interrupted dispatches failed and can resume the stored native thread on a new explicit user turn. It never resubmits an ambiguous paid request.

Backup: stop new dispatches, wait for active turns or record interrupted status, quiesce the runner before copying the complete state volume (broker map plus Codex rollout/state databases), then take a consistent auth+research dump. Keep private per-account manifests/checksums, image/pin metadata and credential source references separate from shared issue artifacts. Restore the DB and matching home together into an isolated account runner, with no other users' volumes or credentials. Verify history, full tool arguments/results and a new explicit real-provider turn after process restart. The supplied offline protocol fixture proves only fixture process persistence, not native/provider recovery.

Initial **unmeasured planning estimate**: one native runner per active user, start with 512Mi memory/0.5 CPU request and 2Gi/1 CPU limit plus one account PVC; API/DB costs are separate. Single-node scheduling must budget the aggregate maximum active users and measure startup/model turn/history read memory before selecting limits. No cluster size/capacity or purchased resource has been assumed. Idle runner shutdown can retain the volume and map; relaunch must use exactly the same account mapping and explicit personal authentication.
