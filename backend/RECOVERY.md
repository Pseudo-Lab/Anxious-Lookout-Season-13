# M3 isolated recovery rehearsal

This supplements the existing full DB backup and auth-only invariant checks. It is development evidence and reviewed procedure source, not authorization to modify an operating DB, deploy a runner or consume a model credential.

The existing `infra/hosting/db-backup.sh` already dumps the complete DB with --no-owner/--no-privileges, private atomic archive/checksum publication and collision protection. Do not create a second dump implementation. `app.restore_research` accepts a separately supplied RESTORE_DATABASE_URL, an explicit matching `restore_*` candidate name and --confirm-isolated-candidate; it never defaults to ADMIN_DATABASE_URL or silently initializes/resets a schema. It validates the frozen M2/research structures first, then reapplies only reviewed GRANT/REVOKE statements from immutable migration inputs. Existing app role passwords remain unchanged. It validates effective table/column grants afterward and rejects unexpected privileges. It revokes old browser/OAuth/tool grants, marks interrupted conversations failed and retains private materials, versions, relations, retry records, contexts and conversation originals/cache. Reconcile approval changes made since the dump before real recovery.

## Reproduction

Build the test/runtime images from the shared task SHA using [INTEGRATION.md](INTEGRATION.md), create the dedicated backend integration-smoke project and seed its owned disposable records using Docker-only tests.integration_probe. Source credentials are only fixture inputs. To build the original image, use `git archive` of the exact baseline into a separate /tmp context, then Docker build its runtime target (never a host language build).

Add `-f backend/compose.m3-recovery.yml` after `-f backend/compose.m3-integration.yml`; keep `-p anxious-s13-back-m3-integration-smoke` and port28110. Start m2-api, then `run --rm recovery` for the original-image/data probe. After the existing backup script produces a new absolute private archive, use the fixture db service to create the explicit restore candidate and restore that archive. Run `run --rm recovery python -m tests.recovery_probe restore` for full row/hash, grant and readiness checks. See the test module for exact assertions. Repeating a rehearsal needs a fresh explicitly owned candidate/project; do not delete or overwrite an unknown existing DB.

For an actual reviewed recovery: stop new turns, quiesce each account runner and preserve its matching complete owner-marked home/ledger volume; obtain consistent DB/native backups with private manifests/checksums and exact image/pin metadata. Restore into new isolated candidates, verify structure and data before grant reapplication, keep account IDs unchanged, invalidate old browser/tool grants, reconcile current approval authority, attach only that owner's preserved home and explicitly approved personal credential, then validate history and a new explicit provider turn after process restart. PM executes authorized reviewed procedures; actual infrastructure/credential/provider validation is pending. No automatic paid replay or destructive downgrade is part of rollback/recovery.
