# Codex operator-funded authentication: investigation only

2026-10-08, issue #6. No credential inspection, provider login, inference, paid resource or operating change was performed. Authentication selection and its actual validation still need explicit user/PM inputs.

[Official authentication](https://learn.chatgpt.com/docs/auth) describes ChatGPT and API-key sign-in, with separate API billing. [Official app-server plan integration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) describes tokens authorized for the user's own ChatGPT plan. Those pages do not establish that one operator's personal subscription can be reused for arbitrary platform members; that option remains unconfirmed. [API production guidance](https://developers.openai.com/api/docs/guides/production-best-practices) supports server-side secret/project access and spending controls.

Code feasibility: runner Native currently reads CODEX_API_KEY_FILE and sends account/login/start(apiKey) over private stdio. The provider billing identity is separate from auth.accounts.id, which selects the runner and scopes every document/material/session/tool grant. Thus an explicitly authorized operator API project could fund use while every platform account retains its own runner/home/ledger/state/token. The service would never expose that project key to the browser or treat it as platform admin authority. No implementation choice enabling shared operator credentials was made.

Current constraints: one mapped runner/state per platform account; private Secret input, explicit model, no inherited DB/operator environment; active native thread/turn/call binding and current approved-editor/admin checks; no credential-refresh/generic raw RPC surface. Offline factories reject model credentials entirely. API-key billing does not prove selected-model access, real resume or acceptable deployment capacity. ChatGPT/browser/device-token lifecycle, account eligibility and operator-plan multi-user support are not implemented or validated by this API-key prototype.

Needed before real validation: selected supported authentication/billing approach, authorized project/Secret delivery and revocation, explicit model/usage budget, fixture-to-real test account UUID, account-specific persistent runner placement/network/volume/backup boundary, and reviewed model inference/restart/resume procedure. Existing local PM/developer login caches are not inputs. A new user decision can authorize this later; the current policy message permits investigation only.
